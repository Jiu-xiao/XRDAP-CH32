# XRDAP-CH32

[中文](README.md)

XRDAP-CH32 is CMSIS-DAP v2 debug probe firmware for the WCH CH32V307, CH32V305 and CH32V208, built on [libxr](https://github.com/xrobot-org/libxr) and part of the XR-DAP family. Keil, pyOCD, probe-rs and OpenOCD use it as an ordinary CMSIS-DAP probe. Two probes with a radio form a wireless probe: one is plugged into the computer, the other is wired to the target. The firmware also implements the XR vendor extension, with which the host tool of [XRDAP-Host](https://github.com/Jiu-xiao/XRDAP-Host) reads and writes variables and has the probe sample them at a fixed period. The code shared by the XR-DAP probes is in [XRDAP-Core](https://github.com/Jiu-xiao/XRDAP-Core).

## Boards

| Firmware | Board | Chip and clock | USB | Radio |
|---|---|---|---|---|
| `wdap` | High-speed wireless DAP board | CH32V307RCT6, 216 MHz | High speed, 480 Mbit/s | SX1281 module |
| `wdap-144` | Same | CH32V307RCT6, 144 MHz | High speed, 480 Mbit/s | SX1281 module |
| `v305` | CH32V305 board (the WCH-LinkE circuit) | CH32V305FBP6, 216 MHz | High speed, 480 Mbit/s | None |
| `v305-144` | Same | CH32V305FBP6, 144 MHz | High speed, 480 Mbit/s | None |
| `linkw` | WCH-LinkW-R0-1v1 | CH32V208GBU6, 144 MHz | Full speed, 12 Mbit/s | The chip's own radio |

The CH32V307 and CH32V305 are rated for 144 MHz. SWD is generated by GPIO in software, and its speed scales with the core clock, so `wdap` and `v305` run at 216 MHz; the chip runs hot at this clock and may restart. `wdap-144` and `v305-144` are the same boards at the rated clock. Pins, lights and keys of each board are in [docs/boards.en.md](docs/boards.en.md).

## Flashing and updates

Every release has the files below. `<firmware>` is `wdap`, `wdap-144`, `v305`, `v305-144` or `linkw`; `<board>` is `wdap`, `v305` or `linkw`, and the two clocks of a board share its boot files.

| File | Contents | Used for |
|---|---|---|
| `xrdap-ch32-<firmware>.bin` | Firmware | Every update |
| `xrdap-ch32-<board>-bootloader-a.bin`, `xrdap-ch32-<board>-bootloader-b.bin` | The images of the two bootloader slots | Updating the bootloader, when the release notes say so |
| `xrdap-ch32-<board>-boot-chain.bin` | Boot chain: stage 1 and one bootloader | The first flashing of a new board |
| `xrdap-ch32-<board>-migrate-to-ab.bin` | Migration image (not for `linkw`) | Moving a board with a bootloader older than 0.6 to the new boot chain |
| `SHA256SUMS` | Checksums of these files | |

An update needs only a USB cable and a browser: the [XR-DAP CH32 firmware update](https://jiu-xiao.github.io/XRDAP-CH32/) page in Chrome or Edge takes the firmware file and, after Start and the choice of the probe in the device list, restarts the probe into its bootloader and writes the firmware; the probe then starts the new firmware. The first time the browser meets a probe's bootloader it asks for access once more. With "Update the bootloader as well" and the two slot images picked, the page writes both slots in turn, then the firmware. dfu-util and this repository's `tools/dfu_update.py` write it as well; the commands are in [docs/boot.en.md](docs/boot.en.md).

A new board first gets the boot chain. A WCH-Link writes it, for example the boot chain of `wdap` with the WCH OpenOCD shipped with MounRiver Studio and this repository's `tools/wch-riscv.cfg`:

```
openocd -f tools/wch-riscv.cfg -c init -c halt -c "flash erase_sector wch_riscv.flash 0 last" -c "program xrdap-ch32-wdap-boot-chain.bin 0x00000000 verify" -c "reset run" -c shutdown
```

The bootloader then stays in DFU mode, and the firmware is written as above. `v305`, `linkw`, boards without a debug header and boards with older firmware are written differently; see [docs/boot.en.md](docs/boot.en.md).

With the board's bootloader key held at power-up, the bootloader stays in DFU mode and does not start the firmware; this is the way back when the firmware does not start or a write was interrupted.

On the computer the probe is the USB device `1D50:6199` with the serial `XRobot-XRDAP-` followed by the chip UID; the bootloader is `1209:3072`. On Linux these udev rules give ordinary users access to both:

```
SUBSYSTEM=="usb", ATTR{idVendor}=="1d50", ATTR{idProduct}=="6199", MODE="0666"
SUBSYSTEM=="usb", ATTR{idVendor}=="1209", ATTR{idProduct}=="3072", MODE="0666"
```

## Wireless debugging

Two `wdap` or two `linkw` boards form a wireless probe, both with the same firmware. They are paired first: within 10 s, the pairing key is held for 3 s on one board and then on the other (KEY2 on `wdap`, ModeS on `linkw`). The pairing is stored in flash and survives power cycles and updates. The pairing parameters tell pairs apart; they do not authenticate.

The roles are chosen automatically. A paired probe without a debug session of its own is the remote and listens on the radio; when a debug tool on the computer sends DAP_Connect to one of the probes, that probe looks for its paired remote: if it answers, the DAP commands of this session run over the radio on the remote's SWD port, otherwise the probe works as an ordinary wired probe. The board that is only powered is therefore the remote and the board on the computer the host; on the computer the probe is used as a wired one.

The role (auto, wired, host, remote), the air rate (high, low) and the channel (auto or locked) are kept in the settings area of the flash and changed with control port requests, described in section 8 of XRDAP-Core's [`docs/protocol.en.md`](https://github.com/Jiu-xiao/XRDAP-Core/blob/main/docs/protocol.en.md), together with the packet format, sessions and channel rules of the radio link. `wdap` uses an SX1281 module and `linkw` the chip's own radio; their air formats differ, so a board pairs only with a board of its own kind.

## Reading and sampling variables

With the XR vendor extension one command reads or writes several addresses and follows pointer chains, and the probe samples variables at a fixed period that does not depend on the USB round trip. `read`, `write` and `watch` of `xrdap` use these commands:

```
xrdap read --elf app.elf motor.speed motor.state
xrdap watch --elf app.elf motor.speed motor.current --period 1ms --csv log.csv
```

In wireless debugging these commands are forwarded to the remote as well, and the remote samples. The command formats are in section 3 of XRDAP-Core's `docs/protocol.en.md`.

## Building

Building needs CMake 3.21 or newer and WCH RISC-V GCC 15.2 or newer (`riscv32-wch-elf-gcc` on `PATH`, or `-DCOMPILER_PREFIX=<path>/riscv32-wch-elf-`). Each firmware is a preset in `CMakePresets.json`, and a preset builds the application and the board's boot chain:

```
git clone --recursive https://github.com/Jiu-xiao/XRDAP-CH32.git
cd XRDAP-CH32
cmake --preset wdap
cmake --build --preset wdap
```

The application is `build/wdap/xrdap.elf.bin`, the boot chain is in `build/wdap/bootloader/`. `tools/build.sh` builds every preset and collects the images in `build/images/<preset>/`; CI runs it in the `xrimage/xrimage-ch32-riscv` container and creates a draft release when a `v*` tag is pushed.

The flash layout, the bootloader slot rules, the target reset pin, the sampling tick and the `linkw` radio driver have tests on the build machine:

```
cmake -S tests -B build/tests
cmake --build build/tests
ctest --test-dir build/tests
```

The DFU part of the update page is tested under Node: `node --test web/test/dfu.test.mjs`.

The version is `XRDAP_VERSION` in `cmake/xrdap.cmake`; the build appends the commit, for example `0.6.0+g2ec5b8e`.

## Directories

| Directory | Contents |
|---|---|
| `boards/<board>/` | Everything of one board: `board.cmake` (chip family, crystal, core clock, flash layout, sources of the parts), `board.hpp` (pins, LED, SWD timing), `board.cpp` (puts the probe and the parts together and runs the main loop), and the parts only this board uses |
| `chips/<family>/` | The WCH SDK, startup file, clock and USB definitions and compiler settings (`chip.cmake`) of one chip family; the linker script `chips/Link.ld` serves both families |
| `app/` | The application parts every board uses: the probe (`probe`), the part interface (`part`), the sampling tick, the settings, the watchdog |
| `bootloader/` | Stage 1, the DFU bootloader and the migration image, a CMake project of its own that the application project builds |
| `common/` | Definitions the application and the bootloader share: flash layout, slot records, clock |
| `cmake/xrdap.cmake` | Build settings, defaults and version shared by both projects |
| `tests/` | Tests on the build machine |
| `tools/` | Build script, update script, boot chain packer, WCH OpenOCD configuration |
| `web/` | The firmware update page (WebUSB DFU), published on GitHub Pages; `web/test/` tests its DFU part under Node |

A new board needs a directory `boards/<board>/` and a preset in `CMakePresets.json`.
